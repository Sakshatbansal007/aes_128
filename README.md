# AES-128 engine in Verilog - CS203 Group 6

Encrypt/decrypt AES-128 in hardware, built three different ways (compact, iterative,
pipelined), plus CBC and CTR modes on top. Everything is simulated with Icarus Verilog and
checked against a Python golden model.

## Folder layout

```
rtl/
  sbox.v                 S-box + inverse S-box (generated by scripts/gen_sbox.py)
  sub_bytes.v            SubBytes / InvSubBytes
  shift_rows.v           ShiftRows / InvShiftRows
  mix_columns.v          MixColumns / InvMixColumns (GF(2^8))
  key_expand_round.v     one step of the key schedule
  aes128_core.v          ARCH 1: iterative, 128-bit, one round per clock   (stage 2)
  aes128_compact.v       ARCH 2: 32-bit datapath, 4 shared S-boxes, on-the-fly key
  aes_round_comb.v       one full round (enc+dec), used by the pipeline
  aes128_pipe.v          ARCH 3: 11-stage pipeline, one block per clock
  aes_modes.v            CBC / CTR wrapper around a core
tb/                      testbenches (unit, KAT, random, modes, equivalence, coverage, perf)
scripts/                 python golden model + vector generators + synthesis scripts
vectors/                 generated test vectors
docs/                    stage 3 report and saved results
regress.sh               one-command regression
run_tests.sh             the original stage 2 script (unchanged)
.github/workflows/       CI
```

## Running it (Windows: PowerShell + Ubuntu on WSL)

One time, inside Ubuntu:

```
sudo apt install iverilog yosys python3-pip gtkwave
pip install pycryptodome --break-system-packages
```

Then from PowerShell, in the project folder (the one that contains `rtl/`):

```
wsl bash regress.sh quick      # about 3 minutes
wsl bash regress.sh full       # all 10,000-vector runs, slow (Icarus), go get chai
wsl bash regress.sh unit       # only the unit tests
wsl bash regress.sh perf       # cycle counts
wsl bash regress.sh synth      # yosys area numbers
```

Use `bash regress.sh`, not `./regress.sh`, because unzipping on Windows drops the execute bit.
If bash complains about `\r`, the file got Windows line endings: `wsl sed -i 's/\r$//' *.sh scripts/*.sh`.
Running inside `/mnt/c/...` is slower than inside your Linux home; copy the folder to `~` if
simulations feel too slow.

Logs go to `logs/`. Waveform of the NIST test: `sim/nist.vcd` (open in GTKWave).

## The three architectures

| | Compact | Iterative | Pipelined |
|---|---|---|---|
| file | `aes128_compact.v` | `aes128_core.v` | `aes128_pipe.v` |
| datapath | 32 bit (one column / clock) | 128 bit (one round / clock) | 128 bit x 10 round stages |
| round keys | one key register, updated on the fly | all 11 stored | all 11 stored |
| cycles per block | 53 enc / 63 dec | 23 (incl. key schedule) | 1 (11 latency, after 11-cycle key setup) |

Compact and iterative share the same ports (`start`, `enc`, `key`, `din`, `dout`, `done`), so
the same testbenches run on both. The pipelined one is different: load the key once with
`key_load`, wait for `key_ready`, then give a block with `in_valid` every clock. Do not
reload the key while blocks are still inside the pipeline.

## Modes

`aes_modes.v`: pulse `init` with key and IV (CTR: initial counter block), then pulse
`blk_start` per 128-bit block and wait for `blk_done`. CTR always runs the core in encrypt
direction, and the counter is incremented as a full 128-bit number (as in SP 800-38A).
Works with the compact core too: `iverilog -DMODES_CORE=aes128_compact ...`

## Verification summary

Unit tests (S-box all 256 inputs, ShiftRows, MixColumns, key expansion) - FIPS-197 and SP 800-38A
known answers - 10,000 random vectors vs pycryptodome on every architecture - random CBC/CTR
messages - round trips - cross-architecture equivalence - functional coverage. Details and
numbers in `docs/STAGE3_REPORT.md`.
